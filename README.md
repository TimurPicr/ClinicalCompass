# Clinical Compass 2

Локальный модульный монолит для наблюдения **только за синтетическими пациентами**: FastAPI, React/Vite, PostgreSQL/pgvector, локальные Qwen через Ollama. Русский интерфейс врача и пациента. Это исследовательский MVP, статус не является диагнозом, приложение не обеспечивает непрерывное наблюдение и не заменяет неотложную помощь.

## Быстрый запуск на macOS

Если Homebrew ещё не установлен, используйте инструкции с [официальной страницы](https://brew.sh/).

Требуются Docker Desktop (или совместимый работающий Docker engine), Homebrew, Python 3.13, Node.js 22.12+ и Ollama. Python 3.13 выбран для совместимости бинарных зависимостей; системный Python менять не нужно. Если Docker Desktop уже установлен, запустите его.

```bash
brew install python@3.13 node ollama tesseract tesseract-lang poppler
# При отсутствии Docker Desktop:
brew install --cask docker
open -a Docker
```

Из корня этого проекта:

```bash
cp .env.example .env
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock.txt
npm --prefix app/frontend ci
```

`requirements.lock.txt` фиксирует проверенные версии; `requirements.txt` описывает прямые зависимости. Для обновления используйте отдельное окружение и повторите тесты. Node-зависимости закреплены в `package-lock.json`.

Подготовьте БД (порт **5440** принадлежит этому проекту):

```bash
docker compose up -d --wait db
python -m scripts.init_db
# Та же миграция отдельно:
python -m alembic upgrade head
python -m alembic check
```

`init_db` применяет миграции и добавляет неизменяемые PHQ-9/GAD-7. PostgreSQL слушает только `127.0.0.1:5440`; данные находятся в Docker volume `clinicalcompass2_postgres_data`. Обычный `docker compose down` сохраняет историю. **Не используйте `down -v`, если данные нужны.** Локальный `.env` содержит секреты и исключён из Git. Пароль в `.env.example` предназначен для локальной разработки: при изменении пароля согласуйте `POSTGRES_PASSWORD` и `DATABASE_URL` до первой инициализации volume.

Локальные модели (Ollama устанавливает их на этот Mac):

```bash
# В отдельном терминале, если приложение Ollama ещё не запущено:
ollama serve
# В другом терминале:
ollama pull qwen3:4b-q4_K_M
ollama pull qwen3-embedding:0.6b
ollama lis
```

Идентификаторы проверены по [официальной библиотеке Qwen3](https://ollama.com/library/qwen3:4b-q4_K_M) и [Qwen3 Embedding](https://ollama.com/library/qwen3-embedding:0.6b): 4B Q4_K_M около 2,6 ГБ; embedding 0.6B Q8_0 около 639 МБ, 1024 измерения. Контекст генерации ограничен 8192 токенами. Обработчик использует единый PostgreSQL advisory lock для тяжёлых задач; несколько процессов не запускают генерацию параллельно. API поиска при занятой/недоступной модели использует текст и метаданные. Не выставляйте Ollama в интернет.

Заполните синтетическую демонстрацию:

```bash
python -m scripts.seed_demo --cohort realistic-v2
./scripts/dev.sh
```

Откройте **http://localhost:5174**. API: http://127.0.0.1:8010/docs. Порты выбраны так, чтобы не конфликтовать с обычными 5432/8000/5173. Скрипт запускает backend, frontend, AI-worker и лёгкий планировщик; Ctrl+C останавливает эти процессы, но сохраняет БД. Он не запускает Ollama за вас.

Демонстрационные аккаунты:

| Роль/сценарий                                              | Email              | Пароль    |
| ---------------------------------------------------------------------- | ------------------ | --------------- |
| Врач | doctor.realistic-v2@example.com | DemoDoctor123! |
| Улучшение депрессивной симптоматики | anna.realistic-v2@example.com | DemoPatient123! |
| Тревога, пропуски, сообщение о тошноте | pavel.realistic-v2@example.com | DemoPatient123! |
| Ухудшение, положительный пункт 9 PHQ-9 | maria.realistic-v2@example.com | DemoPatient123! |
| ГТР, обсуждение фармакотерапии | andrey.realistic-v2@example.com | DemoPatient123! |

Все имена, назначения, результаты и документы вымышлены. Seed не изменяет существующие аккаунты, не создаёт фиктивных AI-ответов и не подставляет искусственные эмбеддинги. Сводки и индексация появляются после работы настоящих моделей. Тестовый источник RAG явно помечен синтетическим, его нельзя считать медицинским доказательством. Для изоляции браузерных сессий используйте обычное и приватное окно.

Каждая новая история содержит 21 день дневника, PHQ-9 и GAD-7 в трёх точках, согласованные анамнез, обследования, чат и документ. Приёмы связаны с исторической версией назначения. У Андрея Авиандрова лекарство ещё не назначено: в карте описано ГТР и обсуждение Авиандра на врачебном приёме, решение остаётся врачу. Красный сигнал Марии основан на пункте 9 PHQ-9 и работает при `DEMO_RULES=false`. [Сценарии и ожидаемые результаты](docs/demo-scenarios.md).

Уже существующая демонстрация сохраняется. `--cohort realistic-v2` создаёт отдельного врача и пациентов без смешивания старых и новых историй. Повторный запуск идемпотентен; для нового набора можно выбрать другое имя cohort. Запуск без `--cohort` сохраняет привычные адреса `doctor@example.com`, `anna@example.com` и т. д. и пропускает существующие аккаунты. Пароли выше относятся к вновь созданным аккаунтам.

## Запуск процессов отдельно

Каждая Python-команда выполняется из корня после `source .venv/bin/activate`:

```bash
python -m uvicorn app.backend.main:app --host 127.0.0.1 --port 8010 --no-access-log
python -m app.backend.ai.worker
python -m scripts.scheduler
npm --prefix app/frontend run dev -- --host 127.0.0.1 --port 5174
```

Используйте **один ASGI-процесс**: WebSocket-рассылка держит текущие соединения в памяти, сообщения сохраняются в PostgreSQL. Несколько AI-worker допустимы, но задачи выполняются последовательно. Scheduler каждые 30 секунд проверяет временные правила и отправляет напоминания; транзакционный advisory lock предотвращает параллельные проходы. Worker ставит синхронизацию источников раз в `KNOWLEDGE_SYNC_HOURS` (по умолчанию 24); `0` отключает автоматическую проверку.

Проверка отдельной задачи:

```bash
python -m app.backend.ai.worker --once --no-sync
python -m scripts.scheduler --once
```

## Создание врача и восстановление доступа

Публичной регистрации врачей и административной панели нет:

```bash
python -m scripts.create_doctor --email clinician@example.com --name 'Имя врача' --timezone Europe/Moscow
```

Скрипт запрашивает пароль скрытым вводом (минимум 12 символов). Врач создаёт приглашение в интерфейсе и передаёт полученную ссылку пациенту самостоятельно. Ссылка привязана к email, срок по умолчанию 48 часов, максимальный 7 суток; повторное использование запрещено, прикрепление к врачу происходит в той же транзакции.

В MVP восстановление выполняется разработчиком **после проверки личности**:

```bash
python -m scripts.reset_password --email clinician@example.com
```

Команда выдаёт ссылку на один час. Пользователь открывает её и устанавливает пароль; все предыдущие сессии отзываются. Автоматической почтовой рассылки нет. Не публикуйте ссылки, пароли и `.env`. Access-логи в рекомендуемых командах выключены; дополнительный фильтр удаляет query-токены из uvicorn access logs.

## Проверка полного сценария

1. Войдите врачом, создайте приглашение на новый email.
2. Откройте ссылку в приватном окне, зарегистрируйте пациента; он появится у нужного врача.
3. Врач открывает карту, вводит дату рождения, диагноз F00–F99, анамнез и аллергии. Пациент может дополнять собственные сведения, но не устанавливает диагноз.
4. Врач создаёт назначение препарата с ежедневными временами приёма и назначает PHQ-9/GAD-7 либо собственный опросник. Конструктор поддерживает одиночный/множественный выбор, число и текст, порядок вопросов.
5. Пациент отмечает предусмотренный расписанием приём или пропуск, при необходимости фактическое время/жалобу, заполняет опросник и дневник. Шкалы дневника подписаны направлением оценки.
6. Сразу обновляются правила и очередь AI. Сбой Ollama не откатывает ответ и не останавливает обычные функции.
7. Запустите worker; врач видит сводку, факты, гипотезы, рекомендации для рассмотрения, источники и время. Пациент получает отдельную краткую сводку. При отсутствии результата отображается честный статус задачи.
8. На Марии нового набора проверьте красный сигнал по пункту 9 PHQ-9. Врач может просмотреть, подтвердить или отклонить предупреждение, добавить комментарий; история действий сохраняется. AI не понижает критический сигнал и не создаёт его независимую копию при пересказе правила.
9. Измените дозировку/время: версия и предыдущие значения останутся в истории. Старый приём связан со старой версией.
10. Импортируйте разрешённый медицинский источник в «Базе знаний», дождитесь индексации, выполните поиск. Результаты содержат исходную ссылку и страницу, если документ размечен по страницам.
11. Пациент загружает PDF/фото. Worker извлекает текст и предложения с цитатой/страницей; врач подтверждает или отклоняет их. Подтверждённая карта **не перезаписывается**: врач переносит нужные сведения отдельным редактированием с аудитом.
12. Отправьте сообщения и вложение из двух окон. История после обновления страницы сохраняется, WebSocket обновляет открытую комнату. Чужой врач получает 404.
13. Настройте VAPID и подписку, оставьте server + scheduler работающими, назначьте задание на ближайшее время. Push содержит только нейтральное предложение открыть приложение.

Автоматический интеграционный прогон с **настоящим PostgreSQL и HTTP/WebSocket**, без модели:

```bash
python -m scripts.smoke_api --base-url http://127.0.0.1:8010
```

Скрипт создаёт уникальные синтетические данные и сохраняет их для проверки. Он не удаляет медицинскую историю. Для реальных локальных моделей:

```bash
python -m scripts.check_local_ai
# ID пациента возвращает GET /api/patients:
python -m scripts.check_local_ai --patient-id 2
# Содержательные регрессии с настоящей моделью (шесть случаев):
python -m scripts.evaluate_ai --output var/evaluations/ai-evaluation.json
```

Первый вызов проверяет реальный embedding и структурированный JSON; второй — очередь, RAG и полный AI-анализ. Не запускайте параллельно длительные model-smoke и worker: глобальная блокировка вернёт состояние «занято». Интеграционный CLI сначала индексирует до десяти ожидающих источников, затем обрабатывает собственную задачу пациента; посторонние OCR-задачи он не выполняет. Ошибки OCR или источников не считаются успешным выполнением.

`evaluate_ai` проверяет улучшение и ухудшение, исторический критический ответ вне окна последних анкет, конфликт аллергий, отсутствие назначений у Андрея и prompt injection. Пациенты создаются в изолированной SQLite в памяти; настроенная PostgreSQL используется только для общего lock с worker. Отчёт сохраняет вход, ответ, отклонённый валидатором результат и отдельные проверки. Ошибка возвращает ненулевой exit code. Эвристики текста и ручное врачебное ревью описаны в [docs/ai-evaluation.md](docs/ai-evaluation.md); успешный JSON не означает медицинскую достоверность.

## RAG и внешние источники

Подробности и первичные ссылки: [docs/sources.md](docs/sources.md). Проверяемые правила: [docs/clinical-rules.md](docs/clinical-rules.md).

- PubMed использует E-utilities `esearch`/`efetch`. По умолчанию сохраняется библиография, а не произвольно скопированные аннотации. Для PMC открытый текст импортируется только при явной разрешающей лицензии через официальный OAI API. Размеры ответа и частота запросов ограничены.
- ГРЛС и рубрикатор Минздрава диагностируются; несуществующий API массовой выгрузки не выдумывается, CAPTCHA/авторизация не обходятся. Если доступного адаптера выгрузки нет, журнал прямо сообщает `manual_import_required`, доступен локальный импорт легально полученного файла.
- Документ получает checksum и номер версии. Неизменившийся текст не индексируется повторно; предыдущая активная версия остаётся доступной до успешной индексации новой. Извлечённые LLM факты помечены непроверенными и не становятся критическими правилами.
- Клинический анализ исключает синтетические примеры и библиографические карточки без полного текста. RAG выбирает ограниченное число фрагментов, проверяет ID/URL/страницы цитат и передаёт ограниченный контекст. Подстановка неизвестной ссылки модели приводит к ошибке/повтору, а не публикации фиктивного источника. Защита от prompt injection снижает риск, но не гарантирует медицинскую корректность генерации.

Ручная проверка источников:

```bash
python -m scripts.sync_sources
```

Локальный импорт (UTF-8 TXT или PDF; файл и ссылка должны соответствовать разрешённому источнику):

```bash
python -m scripts.import_knowledge /path/to/document.pdf \
  --source minzdrav --external-id source-document-id \
  --title 'Название и редакция рекомендации' \
  --url 'https://cr.minzdrav.gov.ru/' \
  --category clinical_guideline --version '2026' \
  --ingredients 'вещество 1,вещество 2'
```

Категории: `drug_instruction`, `clinical_guideline`, `publication`. OCR работает локально, требует `tesseract` с `rus+eng`, а для сканов PDF — `pdftoppm` (Poppler). До 60 страниц и 15 МБ, читаемые изображения до 30 мегапикселей. Нечёткие фото, таблицы, рукопись и необычная вёрстка ухудшают качество; подтверждение врача обязательно. Исходный файл лежит в закрытом `var/uploads`, доступен только через авторизованный endpoint, а не статическую раздачу.

## PWA и Web Push

```bash
python -m scripts.generate_vapid
```

Скопируйте обе строки в `.env`, укажите `VAPID_CONTACT=mailto:ваш-email`, перезапустите backend и scheduler. Секретный ключ нельзя коммитить. Пациент включает напоминания своей кнопкой; разрешение браузера запрашивается только после действия пользователя. При отсутствии поддержки/настроек интерфейс объясняет ограничение. Поддерживаемые endpoint-домены: Google FCM, Mozilla, Apple, Windows Push; произвольные URL и локальные адреса не принимаются.

Нужен HTTPS (localhost допускается браузерами для разработки). На поддерживаемых iOS/iPadOS Web Push требуется установленное на домашний экран веб-приложение; запрос выполняется по нажатию пользователя. См. [официальное описание WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/). Отправка идёт через стандартную инфраструктуру push браузера, но сообщение не содержит диагнозов, препаратов или иных медицинских данных. Без работающего MacBook, scheduler и сети уведомления не отправляются. Service worker не кеширует медицинские API/файлы; полноценного офлайн-режима нет.

## Доступ с другого устройства через HTTPS

Сначала используйте только синтетические данные. Публичный адрес обслуживает **один backend**, который раздаёт собранный React и `/api` + `/ws` с одного origin:

```bash
npm --prefix app/frontend run build
brew install cloudflared
python -m uvicorn app.backend.main:app --host 127.0.0.1 --port 8010 --no-access-log
# В другом терминале:
cloudflared tunnel --url http://127.0.0.1:8010
```

Quick Tunnel выдаст временный `https://....trycloudflare.com`. Запишите этот адрес в `PUBLIC_URL`, добавьте его в `ALLOWED_ORIGINS`, установите `COOKIE_SECURE=true`, перезапустите backend/worker/scheduler и открывайте приложение только по HTTPS-адресу. Для локального HTTP после этого верните `COOKIE_SECURE=false`, иначе cookie не будут работать. Frontend повторно собирать не требуется: URL API относительные.

Для быстрого запуска без ручной смены `.env` предусмотрен отдельный скрипт:

```bash
python -m scripts.share
```

Он выбирает свободный loopback-порт, запускает временный HTTPS-туннель, backend с `Secure` cookie и точным публичным origin, worker и scheduler. Существующие локальные настройки `.env` не меняются. Ctrl+C останавливает только принадлежащие ему процессы. Требуются уже подготовленная БД, собранный frontend и работающая Ollama. `--no-workers` оставляет только API/туннель для сетевой проверки; `--port` позволяет выбрать конкретный свободный порт. Временная ссылка меняется после перезапуска, приглашения от старого домена придётся создать заново.

Для постоянного домена используйте `cloudflared tunnel login`, `cloudflared tunnel create clinical-compass`, `cloudflared tunnel route dns clinical-compass compass.your-domain.ru` и пример [docs/cloudflared.yml.example](docs/cloudflared.yml.example). Затем `cloudflared tunnel --config /path/to/config.yml run`. WebSocket идёт через тот же туннель. PostgreSQL и Ollama остаются на loopback, отдельные туннели к ним не нужны. Credentials туннеля хранятся вне репозитория. Настройка реального домена/аккаунта выполняется владельцем; внешняя доступность и доставка Web Push проверяются отдельно на целевом устройстве.

## Тесты и реальные ограничения

```bash
python -m pytest -q
npm --prefix app/frontend test
npm --prefix app/frontend run build
python -m alembic check
```

Pytest не требует Ollama и PostgreSQL: SQLAlchemy работает на изолированной SQLite только для быстрых unit/API-тестов, модели мокируются HTTP-ответами в тестах. Production и `smoke_api` используют настоящую PostgreSQL с pgvector. Тесты покрывают приглашения/сессии/CSRF/роли, медицинскую карту/аудит, назначения опросников/снимки/баллы, версии лечения и приём, дневник, правила и предупреждения, дедупликацию/повторы/восстановление AI, источники и цитаты RAG, загрузку/права файлов, WebSocket и Web Push с mock-транспортом.

Дополнительные сценарные тесты проверяют согласованность seed, временные границы и будущие данные, независимые сигналы, новые эпизоды после врачебного отклонения, ссылки рисков на события пациента, историческую версию при сокращении контекста и отсутствие постоянной AI-копии красного правила. При известном красном сигнале результат AI отклоняется, если не отражает его красным риском и не начинает пациентскую сводку сообщением о срочной оценке.

Ограничения: ежедневные фиксированные часы препаратов; опросники разово/ежедневно/еженедельно; ручное восстановление через разработчика; нет автоматического подтверждения медицинских данных, офлайн-заполнения, универсального охвата всех заболеваний F00–F99 или внешних каналов уведомления врача. Зелёный статус означает отсутствие сработавшего правила на доступных данных, а не доказанное благополучие. Пропуски данных и AI-ошибки показываются отдельно. Шкалы скрининговые, применимость проверяет врач. Красное демонстрационное правило предназначено только для тестирования (`DEMO_RULES=true`); его отключение не превращает MVP в валидированное медицинское ПО.

Реальная эксплуатация требует отдельной оценки медицинской безопасности, резервного копирования/восстановления, угроз, нагрузки и требований российского законодательства о персональных данных, медицинской тайне и медицинском ПО. Соответствие этим требованиям не заявляется. Ни один модуль не вызывает сторонний AI API.

Фактически выполненные проверки и ограничения окружения: [docs/verification.md](docs/verification.md).
