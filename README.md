# Clinical Compass

Учебная система поддержки врачебных решений (CDSS) для наблюдения за самочувствием. Пациент проходит учебный опрос, видит подтверждённый план, отправляет самоотчёты и сообщения. Врач работает только со своими пациентами, рассматривает предложения, подтверждает планы и получает предупреждения.

**Это демонстрационный прототип, не медицинское изделие и не готовая клиническая система. Все решения о терапии принимает врач. Используйте синтетические данные.**

## Технологии и структура

Python 3.12+; FastAPI, Pydantic 2, SQLAlchemy 2, Alembic, PostgreSQL 16, Argon2 (`pwdlib`), PyJWT; React 19, TypeScript 6, Vite 8. Графики построены на SVG без дополнительной зависимости. Тестирование: Pytest, Vitest и React Testing Library. Для frontend нужен Node.js 22.12+ (в Docker — 24).

```text
app/backend/
  api/             маршруты и проверка ролей
  core/            настройки, сессии, права, даты
  models/          SQLAlchemy-модели
  schemas/         проверка входных данных
  services/        опросники, правила, рабочие процессы, RAG-адаптер
  main.py          единственная точка входа демонстрационного backend
  cli.py           контролируемое создание врача
app/database/
  connection.py    подключение и сессии SQLAlchemy
  migrations/      схема и учебные справочники Alembic
app/frontend/src/
  api.ts           API-клиент: cookie и CSRF
  types.ts         типы ответов
  pages/           вход и кабинеты
  components/      формы, опросы, графики, планы, чат
tests/             изолированные backend-тесты
docs/              аудит, ограничения, отчёт о проверках
```

Корневые `main.py`, `app/database/schemas.py` — сохранённые ранние SQLite/SQLModel-прототипы. Они **не используются** новым стендом; не запускайте их вместо `app.backend.main:app`. `recomendation.py` — существующий опциональный RAG-сервис, код движка сохранён. Модуль `app/backend/services/recommendations/` остаётся источником учебных правил.

## Настройка окружения

Из корня проекта создайте конфигурацию, если `.env` ещё отсутствует:

```bash
cp -n .env.example .env
python3 -c 'import secrets; print(secrets.token_hex(32)); print(secrets.token_hex(32))'
```

Два сгенерированных значения вставьте в `.env`: первое в `POSTGRES_PASSWORD` и пароль внутри `DATABASE_URL`, второе — в `JWT_SECRET_KEY`. Не публикуйте `.env`. Hex-пароль позволяет не заниматься URL-кодированием специальных символов. Если `.env` уже есть, **дополните его**, сохранив действующие реквизиты БД и JWT.

```dotenv
POSTGRES_USER=clinical_user
POSTGRES_PASSWORD=<первое значение>
POSTGRES_DB=clinical_compass
DATABASE_URL=postgresql+psycopg://clinical_user:<первое значение>@127.0.0.1:5432/clinical_compass
JWT_SECRET_KEY=<второе значение>
COOKIE_SECURE=false
ALLOWED_ORIGINS=["http://localhost:5173", "http://127.0.0.1:5173"]
```

`COOKIE_SECURE=false` нужен только локальному HTTP-стенду. При отдельном HTTPS-развёртывании включите `true` и настройте точные доверенные origins. Сессия живёт 30 минут; затем нужен повторный вход. В браузере используйте один адрес последовательно: `localhost` или `127.0.0.1`.

## Запуск всего стенда через Docker

Нужен запущенный Docker Desktop:

```bash
docker compose up --build
```

Откройте http://localhost:5173. OpenAPI: http://localhost:8000/docs. Backend ждёт готовности PostgreSQL, выполняет `alembic upgrade head`, затем запускается. Frontend работает через Nginx и проксирует `/api` в backend на том же origin. Сервисы: `frontend`, `backend`, `db` (PostgreSQL; сетевой alias `postgresql`) и локальная почта `mailpit`. Имя `db` сохранено для совместимости.

Для фонового режима:

```bash
docker compose up -d --build --wait
docker compose ps
docker compose logs --tail=80 backend
```

Данные сохраняются в именованном томе `postgres_data` внутри Compose-проекта. Обычные `docker compose restart` и `docker compose down` том не удаляют. **`down -v` удаляет данные; для обычной остановки не используйте `-v`.** Не меняйте имя Compose-проекта при повторном запуске, если хотите использовать прежний том.

Существующий том PostgreSQL сохраняет исходные логин, пароль и имя БД: изменение `.env` их не меняет. При ошибке `role does not exist` сверьте реальные реквизиты существующего стенда; не удаляйте том. Если есть таблицы без истории Alembic, сначала сделайте резервную копию и сопоставьте схему: первоначальная миграция рассчитана на пустую БД, автоматического небезопасного `stamp` нет.

## Создание врача

Публичной регистрации врачей нет. Администратор выполняет:

```bash
docker compose exec backend python -m app.backend.cli create-doctor --email doctor@example.com --name "Демонстрационный врач"
```

Введите пароль длиной 12–128 символов дважды. Пароль не передаётся в аргументах командной строки и не имеет значения по умолчанию. Для второго врача повторите команду с другим email.

## Локальная разработка без Docker для приложения

Этот режим используется вместо Docker-сервисов приложения. Если полный стенд уже запущен, сначала остановите только backend и frontend:

```bash
docker compose stop backend frontend
```

В Docker остаются PostgreSQL и Mailpit. Данные не удаляются. `./run.sh` обнаруживает уже работающие Docker-сервисы или занятые порты и не запускает дубликаты.

Для локальной разработки:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
docker compose up -d --wait db mailpit
python -m alembic upgrade head
python -m app.backend.cli create-doctor --email doctor@example.com --name "Демонстрационный врач"
python -m uvicorn app.backend.main:app --reload --host 127.0.0.1 --port 8000
```

При прямом запуске локального backend для Mailpit задайте переменные только команде: `SMTP_HOST=127.0.0.1 SMTP_PORT=1025 SMTP_SECURITY=none python -m uvicorn app.backend.main:app --reload`. Скрипт `./run.sh` сам выбирает локальный адрес и порт Mailpit, если SMTP не настроен или указан Docker-хост `mailpit`; настроенный внешний SMTP он сохраняет. Это позволяет использовать тот же `.env` и для Docker.

В другом терминале:

```bash
cd app/frontend
npm ci
npm run dev -- --host 127.0.0.1
```

Vite проксирует `/api` в `http://127.0.0.1:8000`. `./run.sh` также запускает БД, миграции и оба приложения; перед этим настройте `.env` и установите зависимости. Не запускайте локальный backend/frontend на занятых Docker-стендом портах.

## Полный демонстрационный сценарий

1. Создайте врача командой выше. Откройте два разных профиля браузера: врач и пациент.
2. Врач входит и отправляет приглашение на email будущего пациента. Письмо содержит кнопку «Принять приглашение», ссылка действует 48 часов. Локально письмо находится в Mailpit: http://localhost:8025.
3. Пациент нажимает кнопку в письме и входит или регистрируется с тем же email. Приглашение принимается автоматически после входа. Врач обновляет список и открывает карточку пациента.
4. Пациент в календаре выбирает два дня, отвечает на фиксированные вопросы существующего учебного опросника и добавляет свободные заметки. По ответам строится график за месяц. У врача доступны календарь, дневник и предложения существующего движка. Баллы не интерпретируются как диагноз; свободный текст не оценивается автоматически. Изменения записи сохраняют историю, повторное сохранение одинаковых данных не создаёт дублей.
5. Врач рассматривает предложения с комментарием: принятие или отклонение не создаёт назначения.
6. Пациент во вкладке «Связь с врачом» подтверждает запрос срочной связи. Врач обновляет список предупреждений и подтверждает получение. Это веб-запись, не гарантированное экстренное оповещение.
7. Врач создаёт план наблюдения **без лекарств**, затем отдельно подтверждает. Пациент видит действующий план. Для изменений врач создаёт новую версию и подтверждает её; предыдущая сохраняется в архиве.
8. Пациент отправляет самоотчёт о выполнении, пропуске или частичном выполнении, затем сообщение о нежелательном явлении. Врач видит отчёты, предупреждение и отмечает событие рассмотренным с комментарием. Отчёт допускается один на план за московский календарный день, начиная с даты подтверждения.
9. Врач и пациент обмениваются сообщениями в чате: новые сообщения подгружаются автоматически каждые 2 секунды, без WebSocket и ручного обновления. При разрыве связи выполняются повторные подключения; неотправленный текст сохраняется. Время ответа врача не гарантируется.
10. Выполните `docker compose restart`, обновите страницу: данные сохраняются.

### Лекарственная часть и «Авиандр»

В справочнике есть только **непроверенная неактивная заготовка «Авиандр»**, без показаний, доз и противопоказаний. Назначить её нельзя. Действующие регистрация и инструкция в этой работе не подтверждались.

После самостоятельной проверки действующей инструкции ГРЛС врач добавляет **новую полную запись** через «Справочник»: название, регистрационный номер, HTTPS-ссылку на конкретную запись домена `grls.rosminzdrav.ru`, показания, противопоказания и режимы дозирования. Затем отдельно подтверждает ручную проверку с обоснованием. Только после этого запись доступна в редакторе назначений; режим конкретному пациенту определяет врач. В плане сохраняется снимок источника и даты проверки. Программа проверяет структуру реквизитов, но не подлинность и актуальность документа.

Для технических тестов используются явно синтетические записи, не реальные схемы терапии. Не переносите их в реальное применение.

### Существующий RAG (опционально)

Обычный стенд не требует Ollama, Qdrant или LLM. Адаптер отключён: `RAG_ENABLED=false`. Существующий `recomendation.py` не переписан и не запускается в основном Docker-стенде.

Если отдельно настроены его исходные зависимости (`ollama`, `pymupdf`, `qdrant-client`), модели, локальный Ollama и проверенный PDF-корпус `clinical_guidelines/`, можно в отдельном окружении выполнить:

```bash
python recomendation.py --index
python -m uvicorn recomendation:app --host 127.0.0.1 --port 8001
```

`--index` пересоздаёт локальную коллекцию этого прототипа — применяйте только к подготовленному учебному корпусу. Основному backend задайте `RAG_ENABLED=true` и `RAG_SERVICE_URL=http://127.0.0.1:8001/recommend`. Для backend в Docker нужна отдельно доступная приватная сеть/адрес, `127.0.0.1` обозначает сам контейнер; задайте RAG_SERVICE_URL в .env (например, http://host.docker.internal:8001/recommend при корректной приватной сетевой настройке Docker Desktop). Сам RAG-прототип не имеет аутентификации, не публикуйте его наружу.

Из карточки пациента врач задаёт вопрос. История автоматически не отправляется. Черновик сохраняется с названиями PDF, страницами, недостающими сведениями и признаком ожидающей клинической проверки. Ответ без ссылок отклоняется. Ссылки не доказывают клиническую валидность. Адаптер проверен заглушками, работа с реальными моделями/корпусом требует отдельной проверки.

## Роли и безопасность

- Пациент видит только свои записи, подтверждённые планы и свою переписку. Врач — только пациентов, принявших его приглашение.
- Регистрация всегда создаёт пациента; передать роль или произвольный `doctor_id` нельзя. Смена ведущего врача пока не реализована.
- Пароли — Argon2id. JWT хранится в HttpOnly cookie, **не в localStorage**. Сессия проверяется в БД и отзывается при выходе.
- Изменяющие запросы требуют заголовок `X-CSRF-Token` со значением отдельной cookie `cc_csrf`; сервер сверяет хеш с сессией. Включены SameSite=Strict и проверка Origin.
- Исходный `GET /api/questionnaires/demo` публичен: содержит только учебные вопросы. Медицинские записи требуют авторизации.
- Ответы API не кешируются; access-логи Docker-стенда отключены. Тексты сообщений и клинические записи не отправляются в диагностические логи приложением.
- Клинические изменения оставляют записи аудита, планы версионируются. Результаты и отправленные самоотчёты через API не редактируются. Это журнал приложения, не защищённое от администратора внешнее хранилище аудита.

## Основные API

Полная схема доступна в `/docs`.

| API | Назначение |
| --- | --- |
| `POST /api/auth/register`, `/login`, `/logout`; `GET /api/auth/me` | Регистрация пациента и сессия |
| `POST /api/invitations`, `/api/invitations/accept` | Приглашение врача и подтверждение пациента |
| `GET /api/patients`, `/api/patients/{id}` | Список врача и карточка |
| `GET /api/scales`, `/api/questionnaires/demo` | Каталог версий и учебный опрос |
| `POST /api/questionnaires/demo/submit`, `/api/scales/{code}/{version}/submit` | Сохранение ответов и результата |
| `GET /api/patients/{id}/results`, `/series` | История и временные ряды; `scale`, `version`, `start`, `end` |
| `POST /api/urgent-help`; `GET /api/alerts` | Явный запрос связи и предупреждения врача |
| `POST /api/alerts/{id}/acknowledge`; `GET .../deliveries` | Получение предупреждения и попытки доставки |
| `GET /api/patients/{id}/recommendations`; `POST .../{recommendation_id}/review` | История предложений и решение врача |
| `POST /api/patients/{id}/recommendations/generate-rag` | Опциональный существующий RAG |
| `GET /api/drugs`; `POST /api/drugs`, `/api/drugs/{id}/verify` | Внесение и отдельная проверка сведений ГРЛС |
| `GET/POST /api/patients/{id}/plans`; `POST .../{plan_id}/confirm` | Версии планов и подтверждение |
| `GET/POST /api/patients/{id}/adherence`; `GET .../summary` | Самоотчёты и агрегат |
| `GET/POST /api/patients/{id}/adverse-events`; `POST .../{event_id}/review` | Нежелательные явления |
| `GET/POST /api/patients/{id}/messages` | Чат; `after_id` получает новые сообщения |
| `GET/POST /api/patients/{id}/diary`; `GET .../series`, `.../{entry_id}/revisions` | Календарь, фиксированные ответы, свободные записи, график и история изменений |
| `GET /api/patients/{id}/audit` | Прослеживаемость изменений для врача |

Временные границы передавайте в ISO 8601 с часовым поясом, например `2026-10-22T00:00:00+03:00`; без пояса API трактует их как UTC. Каждая пара идентификатор/версия шкалы образует отдельный ряд. Старые POST опроса и preview рекомендаций теперь требуют авторизацию (preview — роль врача): это необходимое изменение защиты API, алгоритмы подсчёта сохранены.

## Тесты

Быстрый backend-набор не подключается к `.env`-базе: каждый тест создаёт временную SQLite-БД и применяет миграции.

```bash
.venv/bin/python -m pytest -q
```

Полный набор на PostgreSQL, включая блокировки конкурентных запросов, миграции вверх/вниз и сравнение схемы:

```bash
docker compose -p clinical-compass-test -f docker-compose.test.yml up -d --wait
TEST_DATABASE_URL=postgresql+psycopg://cc_test:synthetic-test-only@127.0.0.1:55432/clinical_compass_test .venv/bin/python -m pytest -q
docker compose -p clinical-compass-test -f docker-compose.test.yml down
```

Тестовая БД работает на порту 55432 и хранится в tmpfs. Для каждого теста создаётся отдельная схема со случайным именем, которая удаляется после проверки. Защита требует имя БД с окончанием `_test`; не указывайте рабочую БД.

```bash
cd app/frontend
npm ci
npm run test
npm run build
npm run lint
```

React-тесты используют mock API и проверяют вход, регистрацию, ошибки, опрос, чат, права интерфейса, подтверждение плана, повторы запроса связи и разделение графиков. Это компонентные проверки, не замена клинической или полноценной браузерной приёмке. Результаты фактических запусков — в `docs/IMPLEMENTATION_REPORT.md`.

## Резервное копирование и восстановление

Сохранить дамп из настроенного стенда (содержимое не попадает в логи):

```bash
mkdir -p backups
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/clinical-compass.dump
```

Храните дамп вне Git, ограничьте доступ, отдельно настройте шифрование и периодическую проверку восстановления. Для восстановления используйте **отдельную пустую БД**, например `clinical_compass_restore`; рабочая БД не перезаписывается:

```bash
docker compose exec -T db sh -c 'createdb -U "$POSTGRES_USER" clinical_compass_restore'
docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d clinical_compass_restore --no-owner --exit-on-error' < backups/clinical-compass.dump
```

Проверьте восстановленные записи, затем при необходимости направьте отдельный backend на восстановленную БД. Для отката версии приложения заранее сохраните дамп; downgrade миграций, удаляющий заполненные клинические справочники, может быть заблокирован внешними ключами.

## Ограничения и ручные действия

PHQ-9 и GAD-7 неактивны: необходимы валидированные русские тексты, алгоритмы, пороги, источник и права использования. Для новой шкалы добавьте неизменяемое определение новой версии миграцией, зарегистрируйте и протестируйте scorer (`Scored`) в `services/scales.py`; активация допустима только после экспертной проверки. Вопросы и ответы проверяются по определению версии.

Клинических порогов в поставке нет. Таблица `clinical_alert_rules` и реестр `services/alert_rules.py` поддерживают конфигурируемые вычислители; правило исполняется только при `active`, `expert_reviewed`, наличии источника, проверяющего и даты. Заполнение и активация — отдельной экспертно проверенной миграцией, публичного API активации нет. Доступны только явный `urgent_help_requested` и некритическое уведомление о нежелательном явлении. Сохранены канал, попытка, статус и поле времени повтора, но **нет** фонового доставщика SMS/email, повторов и эскалации. `available_in_inbox` означает только наличие записи в веб-кабинете. Клинические правила и надёжную доставку нужно проектировать и проверять отдельно.

Также пока нет восстановления пароля, проверки email, MFA, распределённого ограничения попыток входа, процедуры смены врача, автоматического обновления справочника ГРЛС, пагинации длинных историй, проверенного внешнего неизменяемого аудита. Для публичного или реального клинического использования нужны отдельные медицинская, правовая, регуляторная и эксплуатационная проверки; соответствие законодательству РФ не заявляется.

## Почта приглашений

По умолчанию Docker использует Mailpit: SMTP `mailpit:1025`, почтовый интерфейс http://localhost:8025. Письма реально передаются по SMTP в этот локальный ящик, но **не доставляются во внешние почтовые ящики**. Врач больше не передаёт код вручную. Токен хранится в БД только как хеш; ссылка использует fragment, который не попадает в HTTP access-логи. При открытии ссылки GET не меняет данные: после входа frontend выполняет защищённый POST с CSRF. Повторное принятие того же приглашения тем же пациентом безопасно.

Для настоящей почты укажите реквизиты своего SMTP-сервера (аккаунт и пароль приложения необходимо получить у почтового провайдера):

```dotenv
PUBLIC_APP_URL=https://адрес-вашего-приложения
SMTP_HOST=адрес-smtp-сервера
SMTP_PORT=587
SMTP_SECURITY=starttls
SMTP_USERNAME=имя-пользователя
SMTP_PASSWORD=пароль-приложения
SMTP_FROM=Clinical Compass <ваш-почтовый-адрес>
```

Для SMTPS используйте `SMTP_PORT=465`, `SMTP_SECURITY=ssl`. Режим `none` предназначен локальному Mailpit; передача пароля без TLS запрещена. После изменения `.env` пересоздайте backend: `docker compose up -d backend`. На локальном проверочном стенде `PUBLIC_APP_URL` должен соответствовать адресу интерфейса (порт 5174). Ошибка SMTP возвращается врачу, приглашение не фиксируется в БД. Принятие почтовым сервером не гарантирует попадания письма во входящие; доставка вне Mailpit требует настоящих SMTP-реквизитов и настройки домена.

## Как одновременно тестировать врача и пациента

1. Запустите `docker compose up -d --build --wait` и откройте http://localhost:5173. В обычном окне войдите врачом.
2. Откройте **приватное окно / инкогнито** того же браузера или другой браузер. Перейдите на **тот же** http://localhost:5173 и войдите пациентом. Две обычные вкладки и два обычных окна одного профиля используют общие cookies и не изолируют аккаунты. Два окна инкогнито также могут использовать одну приватную сессию — достаточно обычного плюс приватного окна.
3. Для нового пациента врач отправляет приглашение на его email. Откройте http://localhost:8025 **в окне пациента** и нажмите «Принять приглашение» в письме. Если почта открыта в окне врача, скопируйте ссылку приглашения и вставьте её в окно пациента. Врач не может принять приглашение вместо пациента.
4. Пациент заполняет дневник и отправляет сообщение. Врач обновляет список пациентов, открывает карточку и чат: сообщения появляются автоматически. Для новых записей дневника используйте «Обновить данные» в карточке врача.

Тестовые аккаунты, созданные при перепроверке 23.10.2026: `doctor-test@example.com` и `patient-test@example.com`. Они уже связаны и содержат только синтетические записи. Пароль для текущего локального стенда указан в ответе в чате; автоматического создания таких аккаунтов при запуске нет. Для другой БД создайте своего врача через CLI, пациента — через регистрацию. Приложение доступно на порту **5173**; прежний проверочный порт 5174 больше не используется.
